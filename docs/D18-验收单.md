## 七之二、KV 缓存结构等价验证（用户点出的判据）

**起因**：早先我把「KV 缓存是否命中」写成「未验证项」，理由是 provider 侧命中率不可观测。
用户指出这是把**可判定的事**当成了**不可观测的事**——该问的是「发出去的请求跟预期生成的是不是一样」。

### 判据

> 摘要请求的 `messages` 必须是**正常对话请求 `messages` 的严格前缀**。
> 是则必然命中，不是则必然不命中。

### 真实会话实测（`session-e350d45d`，12MB / 4591 事件 / 1419 表面节点 / 71 工具）

| 检查 | 结果 |
|---|---|
| 摘要 messages 条数 | 1192 |
| 逐字节相同 | **1192 / 1192，零差异** |
| `role`+`content` 逐字段相等 | **1192 / 1192** |
| 严格前缀 | **是** |
| 复用内容量 | 2,184,218 字符 |

### 判别力（防止恒真）

| 实现 | messages 条数 | 是否前缀 |
|---|---|---|
| 新（结构化投影） | 1192 | ✅ 是 |
| 旧（拍平纯文本） | **1** | ❌ 否 |

旧实现把 1192 条压成 1 条纯文本，前缀完全对不上，**一次都命中不了**。判据有区分力。

### 已固化测试 `test/d18-kv-prefix.test.js`

| 用例 | 覆盖 | 何时跑 |
|---|---|---|
| KV1 | 严格前缀（含 system 头，留尾部） | 默认 |
| KV2 | 首条是 system 且逐字节等于正常请求首条 | 默认 |
| KV3 | 无 system 头时逐项前缀、长度相等 | 默认 |
| KV4 | **判别力**：旧实现必须通不过 | 默认 |
| KV5 | 选区含 0 号节点时 system 不重复 | 默认 |
| KV6 | `header.tools` 随请求带出 | 默认 |
| KV7 | 真实会话逐字节前缀（含旧实现反证） | 设 `D18_REAL_SESSION` 才跑 |

真实会话**不进仓库**（含用户对话内容），只做按需开关。

### 反向验证（都实跑）

| 注入的错 | 变红用例 |
|---|---|
| 移除 system 头 | KV1、KV2、KV5 |
| 选区消息倒序（`push`→`unshift`，**条数不变**） | KV1、KV2、KV3、KV5 |

第二条最关键：**条数对、顺序错**是最隐蔽的错误——肉眼与「条数断言」都抓不到，
但 KV 缓存完全失效。测试能抓住它。

### 仍然不可验

| 项 | 原因 |
|---|---|
| provider 侧命中率百分比 | 需 provider 日志；判据不依赖它，但给不出数字 |
| 末尾压缩指令本身 | **必然 miss**，原版同样如此（缓存只能命中前缀） |
| `tools` 浅拷贝的对象身份 | 值相等、身份不同；按内容哈希的实现不受影响，按对象身份的未核验 |
