## 9. ⛔ D14 生产安装中止 —— 宿主契约对齐缺失（2026-10-26 08:4x）

### 9.1 结论

**切换中止，主 profile 零改动。** 起因：装机前按 §8 流程做前置核实时发现硬阻塞——`tiered-compaction` 的引擎**只占了 `compaction` 服务位的名字，没有实现宿主引擎契约**。若按原计划切过去，后果是 `/compact` 命令直接报错、自动压缩完全不再触发（压缩功能整体失效），而**不是**「新插件换个算法继续工作」。

**这个阻塞是 M2-M6 整条链的漏验**：双态 6/6 测的是「服务位归谁」，真实链路 6/6 测的是「engine 自己各层能不能跑」，两者都是**单元级**；从头到尾没有一条验收测过**「宿主拿 `ctx.compaction` 去用，接不接得住」**。

### 9.2 证据：模拟宿主真实调用路径

探针用真实 Cordis `Context` + `apply(ctx, {enabled:true})` 挂载插件，然后照宿主源码的调用方式调：

```
=== 模拟宿主 /compact 命令（command-compact 第 55 行：ctx.compaction.compactNow(...)）===
  ✖ TypeError: svc.compactNow is not a function

=== 模拟 basic 自动压缩钩子（pressure 触发：this.compactIfNeeded(agent,"pressure",signal)）===
  ✖ TypeError: svc.compactIfNeeded is not a function

=== 第 3/4 层在无注入时是否真能跑 ===
  applySoftPressure: 有方法
  summarizeIfNeeded 返回: null   ← 第 4 层静默跳过（engine.js:101 缺 tokenMeter/summarizeFn 即 return null）
```

`ctx.compaction` 实例上的完整方法集实测只有：`config, ctx, engine, name` —— **四个属性，零个宿主契约方法**。

### 9.3 契约对比表

宿主侧参照（`G:\DSH Desktop\resources\app\node_modules\@deepseek-ai\`）：

| 项 | `dsh-compaction-basic`（宿主认可的实现） | `tiered-compaction`（当前） |
|---|---|---|
| 基类 | `extends CompactionEngine`（`@deepseek-ai/dsh-compaction` 导出的抽象类） | 无基类，直接 `extends Service` |
| 依赖注入 | `static inject = ["llm", "tokenMeter", "sessions"]` | 无 `static inject`；全部从 `config` 手动传入 |
| 配置校验 | `static Config = z.object({...})`（Schemastery） | 无 |
| 自动压缩注册 | `_registerAutomaticCompaction()` → `ctx.on("agent/pre-step", ...)`、`ctx.on("agent/status", ...)`、`ctx.on("session/event", ...)` | **零 `ctx.on`**，从不注册任何事件钩子 |
| `compactNow(agent, signal, sourceCommandId)` | 有（`/compact` 命令的唯一入口） | **无** |
| `compactIfNeeded(agent, trigger, signal)` | 有（pressure / context-overflow 两个触发器） | **无** |
| `compactRegion(start, end, agent, signal)` | 有 | **无** |
| `summarize(input, agent, signal)` | 有（子类唯一覆写钩子） | 无（自己另起了 `summarizeIfNeeded`，签名不同） |
| 会话表面操作 | 真改：`shadowedSeqs` / `shadowedRange` / `shadowedTokenCount`，把区间换成一个 summary 节点 | 纯文本变换，**完全不碰会话表面**（`engine.js` 只处理字符串与节点数组） |
| 并发保护 | 同 session 事务锁 | 无 |

**关键认识**：basic 的架构是「引擎自己注册钩子、自己在钩子里判断要不要压、自己完成会话表面改写」。本插件目前的 `engine.js` 是一个**纯函数库**（折叠/落盘/压力/摘要各自可用），但没有任何一层把它接到宿主的调用链上。`M4.5 wiring` 接的是「四层之间的串联」，不是「引擎与宿主之间的契约」。

### 9.4 修复方案（已派程序员，照此实现）

1. `TieredCompactionEngineService extends CompactionEngine`（从 `@deepseek-ai/dsh-compaction` 导入）
2. `static inject = ["llm", "tokenMeter", "sessions"]` —— 依赖从 ctx 注入，**彻底消除 config 手传导致的第 3/4 层静默失效**
3. 实现三入口，内部委托现有 `engine.js` 管线：
   - `compactNow(agent, signal, sourceCommandId)` —— `/compact` 手动命令
   - `compactIfNeeded(agent, trigger, signal)` —— 自动：`trigger` 为 `"pressure"` 时跑第 1-3 层（折叠/落盘/软压力），为 `"context-overflow"` 时跑第 4 层摘要
   - `compactRegion(start, end, agent, signal)` —— 定向压缩区间
   - 返回值形状必须与 basic 一致（含 `shadowedSeqs` / `shadowedRange` / `shadowedTokenCount`），否则宿主日志与 `/compact` 结果渲染会出错
4. 照 basic 写法实现 `_registerAutomaticCompaction()`：`ctx.on("agent/pre-step")` 里调 `compactIfNeeded(agent,"pressure",signal)`；`ctx.on("agent/status")`、`ctx.on("session/event")` 清理 overflow 重试状态。**70% 提醒 / 80% 驱逐必须由这个钩子触发**——现在没有任何钩子，第 3 层实际上永远不会在真实会话里运行。
5. `summarize(input, agent, signal)` 覆写为调第 4 层（替换现在的 `summarizeIfNeeded` 私有签名）
6. **新增验收 A12「宿主契约对齐」**（写进设计稿 §6）：用真实 `Context` 构造，断言四个入口全部 `typeof === "function"`，并各跑一次真实调用断言返回形状；`/compact` 命令路径与 pressure 钩子路径都要探针覆盖

### 9.5 教训（写进流程，不只写进文档）

**单元级验证 ≠ 集成级验证。** 「每个模块都能跑」和「宿主真的来调用时接得住」是两件事，中间那道契约对齐必须单列为一道门。以后凡是要替换宿主已有实现的插件，M 计划里必须有一条「宿主契约对齐」，验收方式固定为**用真实 ctx 走宿主源码里的那条调用路径**——而不是只验证自己模块的方法可用。

这条与 M6 卡点时的教训（wiring 必须单列）是同一类错误：**里程碑按「功能分层」切得太整齐，导致「层与层之间」「插件与宿主之间」的接缝没人负责。** 下次 M 计划里，接缝也要占一个里程碑。
