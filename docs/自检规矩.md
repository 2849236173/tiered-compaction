# 插件自检规矩（dsh-tiered-compaction）

日期：2026-10-27
来源：D16 审计 + 2026-10-27 凌晨三次「测试全绿但真实环境跑不了」失败复盘 + 外部方法论验证（agent-fail-eval / hermes-warm-compaction / Compaction Cliff / Harness Design，验证记录见 §5）。

核心问题：**怎么在写插件时就防止「静默失效」**——测试全绿 ≠ 装配正确 ≠ 真实环境能跑。三档防线：加载期自检（单测可查）→ 装配期自检（单测可查大部分）→ 真实环境验收（必须真环境，CI 日常盯）。

## 0. 静默失效的三种形态（本规矩要防的病，全部为本仓库实例）

| 形态 | 实例（2026-10-27 凌晨） | 根因 | 对应规矩 |
|---|---|---|---|
| 桩失真：测试桩伪造宿主不存在的 API | a12 测试桩 `meter.contextWindow()`——真实 dsh-token-meter 公开面只有 `measure(session, requestHeader)`，无 `contextWindow` 方法 | 桩按想象写，未对宿主 lib 源码核对 | R2 |
| 钩子签名错位：函数第一行 return，零报错 | `agent/pre-step` 钩子按对象解构 `{agent, signal}` 写，宿主是位置参数 `(session, event)`——监听器拿到错位参数第一行就 return，无异常无日志 | 钩子签名单测抓不到（零副作用也是零报错），装配路径没跑 | R6 |
| 死装配：接管类从未被实例化 | M4.5 的 `TieredCompactionEngineService` 在 A12 改造后不再被 apply 注册；引擎与观察者建在另一个死类里——零件测试全过，装配从来没测 | 「装配期」无验收面：测试只证明零件可运行，不证明装配发生 | R5 |

## 1. 加载期自检（写插件时；全部可在单测查）

**R1 依赖面逐 API 自检**（学 hermes-warm-compaction `missing_apis()`）
- 检查动作：插件入口（apply/register）第一件事，对每个依赖的宿主 API 逐个 `typeof x === "function"` 检查——ctx 方法、服务位、钩子名、基类导出符号（如 `CompactionId`/`ManualCompactionError`/`compactCheckpointSource`/`toolPairingBalancedBefore`）。
- 缺失时行为（三件必做，不许只做其一）：①不注册任何服务；②`logger.warning` 列**全**缺失清单（不是第一个）；③保留宿主内置行为（回退语义）。
- 单测断言面：缺 API 桩下「ctx 无本插件服务位 + 有警告日志 + 宿主 compaction 位未被触碰」三条各一例。

**R2 桩必须对宿主源码核对（防桩失真）**
- 检查动作：写宿主桩前，先 grep 宿主 `node_modules/<pkg>/lib` 源码里该 API 的真实签名与返回形状；桩旁注释写「桩形状 = 宿主形状」并带宿主 `file:line` 证据。禁止按想象补桩。
- 单测可查的硬面：桩文件里加一条「宿主 API 真实存在」断言（`import` 宿主包后 `typeof` 检查）——宿主 API 改名/删除时测试直接红，桩失真在单测期暴露。

**R3 钩子名与事件名用常量（防字符串漂移）**
- 检查动作：钩子名（`"agent/pre-step"`）、事务事件名（`compaction/start`/`compaction/summary`/`user/message`/`compaction/end`）、服务位名（`compaction`/`tieredCompaction`）全部提为常量集中一处；写常量时与宿主源码比对一次，留 `file:line` 注释。

**R4 加载冒烟（已有，保留）**
- `node --test "test/*.test.js"` 首测必须是「import apply/detach 成功 + typeof function」。
- 口径注意：Node 24 下 `node --test test/`（目录形式）报 MODULE_NOT_FOUND，全量跑用 glob。

## 2. 装配期自检（单测可查大部分；必须走真实加载路径）

**R5 装配断言：服务位真的被接管（防死装配，最贵教训）**
- 检查动作：enabled=true 路径的单测，断言对象是「`ctx.compaction` 可读且为本插件实例」——**不是**「plugin() 被调用过」。用真实 cordis `new Context()` + `await ctx.plugin(...)` 后读服务位（`test/m45-wiring.test.js` A-wire② 是范本）。
- 附加硬面：断言接管实例上的引擎/观察者真的被构造——`svc.engine.status()` 可读、钩子注册后可触发（接线到死类时此断言红）。
- 反面教材记录：stub 只 push 调用记录不构造实例的写法，测不出死装配；已废弃。

**R6 钩子真实触发断言（防签名错位）**
- 检查动作：每个注册的钩子/监听器，单测用真实 cordis 事件派发（`ctx.emit("agent/pre-step", ...)` 按宿主调用形态传参）触发一次，断言**副作用证据**（session 事务事件出现、日志落盘、状态变化）。
- 铁律：零副作用本身就是失败——「不抛错 = 通过」的钩子测试一律不许合入。
- 范本：`test/a12-contract.test.js` A12②（真实 emit 触发 + 断言 `compaction/end` 出现）。

**R7 构造期冲突探测走真实语义**
- 检查动作：construction-catch 降级路径的单测，用真实 cordis Context 预占槽位（先 `await ctx.plugin(Occupier)`）再 apply，断言降级服务注册且 `bypassMode` 置位（A-wire②b 范本）。不许 stub 模拟报错文案。
- cordis 实测口径（记录在案）：`ctx.plugin()` 返回 thenable fiber，构造发生在 `await` 之后；冲突报错文案 `service "<name>" has been registered at <owner>`。

**R8 全量装配冒烟（真实环境级，CI 可自动化）**
- 检查动作：在真实宿主（DSH Desktop）插件目录加载一次，断言启动日志含接管信息、compaction 服务位持有者正确；headless 沙箱跑双态（`test/m6-dual-state.mjs` 模式）。
- 升级防护：DSH 升级后必跑 `tools/gen-ptc-tc.ps1` 重同步（幂等 + 递归 diff 自检，已有）。

## 3. 真实环境验收（必须真环境；CI 日常盯）

**R9 兼容 CI 对双基线跑（学 hermes-warm-compaction hermes-compatibility.yml）**
- 检查动作：对「最小宿主版（锁 commit）」与「上游最新」各跑一遍真实链路检查；报告记三项：宿主 commit 号（dirty 拒绝）、插件逐文件 SHA-256、检查结果 JSON。
- 检查脚本用真实加载链（真实 PluginManager/钩子注册/middleware 派发），不塞桩；每 case 独立进程 + 临时 home + audit-hook fence 阻断外部操作。
- 频率：每日 cron（上游 main 漂移当日暴露，不等 DSH 升级才发现）。

**R10 真实链路 A4b/A8（留待凭据）**
- 检查动作：有凭据沙箱跑 `test/m6-real-llm.mjs`：截断率对比基线（A4b）+ token 降幅 ≥30%（A8）。
- 铁律：无凭据期间此档**显式标注「未验证」**（README/报告），不许静默跳过。

**R11 摘要质量按「约束保留率」验收（学 agent-fail-eval）**
- 检查动作：真实链路验收不只看「摘要存在/更短」——fixture 预置 5-10 条关键约束（禁 push、区域要求、凭据配置、决策规则），摘要后逐条检查可查性（摘要文本 + 谱系表 + 落盘存档三处）；保留率 <100% 时列缺失清单，不许只报均值。
- 数据支撑：实测摘要漏 86%（pi）/73.6%（Claude）事实、用户约束 96.5% 不在摘要；**关键词检索只捞回 28.1% 丢失约束（约束被改述，词法匹配失灵）**——所以验收按约束清单逐条对，不能靠 grep 摘要文本凑数。
- 反直觉校准（写进价值主张口径）：Harness Design 论文实证「让省略内容可恢复」几乎没有准确增益（模型很少去用）。**「可恢复」的卖点是审计与合规可追溯（谱系表），不是准确率**——验收 A11 口径据此定为「引用不失效」，不承诺「恢复后模型会去用」。

**R12 type-aware retention 是已验证方向（Compaction Cliff）**
- 依据：`/compact` 一轮后仅保 53% 安全规则、五轮后 10%；按类型保留（type-aware retention）是对症药。
- 检查动作：本插件 §3 优先级表（todo/goal/plan/用户消息/摘要节点永不清理）即 type-aware retention 的实现；A3「永不清理零丢失」用例保持硬断言，任何改优先级表的 PR 必须附 Compaction Cliff 引证讨论。

## 5. 来源与验证记录（2026-10-27 web_fetch 实证，非二手转述）

1. **agent-fail-eval**（github.com/epequeno/agent-fail-eval）：README 实证「Compaction summaries omit 86% (pi) / 73.6% (Claude) of extracted facts；user constraints worst: 96.5% (pi) / 72.7% (Claude) absent；keyword retrieval recovers only 28.1% of lost user constraints (pi)——constraints get rephrased, so lexical matching misses them」——与转述一致。**修正两点**：86%/96.5%/28.1% 均为 pi-agent 侧数字（Claude 侧为 73.6%/72.7%/69.3%，转述未注明）；「全历史取证查询 100% 恢复」是**循环上界**（检索词派生自事实本身），README 明示不得当真实缓解结果引用。转述称 MIT 许可，抓取页面未及确认（repo 页截断），未验。
2. **hermes-warm-compaction**（Elevatormusic/hermes-warm-compaction，Apache-2.0）：三件套全部实证——①`warm_compaction/__init__.py` 的 `missing_apis()` 对 CONTEXT_METHODS/HOOKS/MIDDLEWARE/context_engine 逐 API callable 自检；缺失时 `logger.warning("...the plugin registers nothing and Hermes keeps its built-in compressor")`（不注册 + 警告 + 回退内置，三件齐全）✓；②降级链 warm → fallback（auxiliary route）→ ledger-only → stop + 安全错误码 ✓；③`.github/workflows/hermes-compatibility.yml`：`schedule: cron "23 9 * * *"`（每日）+ `matrix: hermes: [minimum, upstream-main]`（minimum 锁 commit 45871e10）+ `source_state()` 记 commit（`rev-parse HEAD` + dirty 拒绝）+ `plugin_hashes()` 逐文件 SHA-256 ✓。且检查脚本（`check_hermes_compatibility.py`/`check_plugin_hermes.py`）走**真实** Hermes PluginManager/PluginContext/register_hook/middleware 链（非桩），audit-hook fence 阻断外部网络/子进程/越界写——R9 的「真实加载链」依据。
3. **反直觉校准**：agent-fail-eval README Related Work 引 *The Compaction Cliff in Long-Running AI Agent Memory*（arXiv 2608.22752：「preserves 53% of safety rules after one round and 10% after five (20 production agent configurations)」，提出 type-aware retention）与 *An Empirical Study of Harness Design for Coding Agents*（arXiv 2609.20804：「making elided content recoverable yielded no accuracy gain because models rarely use it」）——转述与引文一致（README 摘要级引证，未读论文全文，标注为摘要级证据）。
