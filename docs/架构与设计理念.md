## 一、要解决的问题

LLM 长会话的上下文是一个只涨不跌的账本。DSH 默认的压缩策略是**一步到位**：压力到 80% 就调一次 LLM 做摘要，把历史整段替换成一棵摘要节点。

这条路有三个固有代价：

| 问题 | 成因 | 实测表现 |
|---|---|---|
| **贵** | 每次压缩都是一次完整的 LLM 调用 | 高频压缩时延迟与成本显著 |
| **丢信息** | 摘要输出有 token 上限，长内容被截断 | 22,690 次摘要调用中 2,462 次被截断过半 |
| **丢中部** | 先截断再摘要，长消息中间的事实最先丢 | 而这往往是最关键的部分 |

本插件的判断是：**大部分上下文瘦身根本不需要模型参与。**

工具输出里大段是重复日志、超长文件内容、可随时重跑的命令结果——这些用确定性规则就能压掉，且能保证无损可逆。真正需要「理解并概括」的内容，比直觉上少得多。

于是有了四层递进：**把 LLM 从第一道防线退到最后一道。**

## 二、四层管线架构

```
                         工具输出产生
                              │
                              ▼
    ┌─────────────────────────────────────────────────┐
    │  第 1 层 · 无损折叠  (lossless-fold)             │
    │  ─────────────────────────────────────           │
    │  连续重复行 ≥3 次 → 「首行 + …[folded Nx]」       │
    │  每次折叠生成逆变换记录                           │
    │  还原时逐字节校验，错配即抛错                     │
    │                                                   │
    │  成本：零 LLM        可逆性：完全可逆             │
    └────────────────────┬────────────────────────────┘
                         │  折叠后仍超阈值
                         ▼
    ┌─────────────────────────────────────────────────┐
    │  第 2 层 · 落盘  (spill-to-disk)                 │
    │  ─────────────────────────────────────           │
    │  >8 KB（UTF-8 字节）→ 全文写盘 + SHA-256          │
    │  上下文只留头尾预览（5120 字符，4:1）+ 存档路径   │
    │                                                   │
    │  成本：零 LLM        可逆性：全文在盘可回读       │
    └────────────────────┬────────────────────────────┘
                         │
                         ▼
    ┌─────────────────────────────────────────────────┐
    │  第 3 层 · 软压力  (soft-pressure)               │
    │  ─────────────────────────────────────           │
    │  70% 窗口 → 插入提醒（不改历史）                  │
    │  80% 窗口 → 按优先级驱逐易失内容                  │
    │                                                   │
    │  驱逐优先级：                                     │
    │    1. bash/pwsh/edit/write 大输出（不可重放）     │
    │    2. read/grep/glob 结果（可重跑恢复）           │
    │    3. 系统提醒/临时注入                           │
    │    永不驱逐：todo/goal/plan/用户消息/摘要节点     │
    │                                                   │
    │  成本：零 LLM        可逆性：可重放项重跑即恢复   │
    └────────────────────┬────────────────────────────┘
                         │  压力达阈值
                         ▼
    ┌─────────────────────────────────────────────────┐
    │  第 4 层 · 有损摘要  (lossy-summarize)           │
    │  ─────────────────────────────────────           │
    │  阈值 = 窗口 − max(16k, 5%窗口) − 摘要预留(20k)   │
    │  摘要预算提前预留，杜绝截断死循环                 │
    │  摘要前全量存档；摘要后登记谱系                   │
    │  输入不先截断（避免丢中部）                       │
    │                                                   │
    │  成本：一次 LLM 调用   可逆性：摘要前全量存档     │
    └─────────────────────────────────────────────────┘
```

### 为什么是「递进」而不是「并行」

四层是**串联短路**关系，不是四选一：

- 第 1 层折叠后如果已经够小，第 2 层就不落盘（避免一份内容被两层重复加工）
- 前三层无论怎么处理，只要压力没到阈值，第 4 层就不启动
- 仲裁器保证**一份内容只归一层处理**，杜绝多层叠加导致的语义损坏

这个「短路」由 `circuit-breaker.js` 里的仲裁器统一裁决，而不是各层自己判断——集中裁决才能保证不重不漏。

## 三、保真三原则

四层里有两层是有损的（驱逐、摘要）。敢做有损操作的前提，是**每一次损失都可追溯、可恢复**。这三条原则贯穿全部层，是本项目最核心的设计约束。

### 原则一：每层留恢复机制

| 层 | 恢复机制 |
|---|---|
| 1 无损折叠 | 逆变换记录 + 还原时逐字节校验 |
| 2 落盘 | SHA-256 校验 + 全量文件保存在存档目录 |
| 3 软压力 | 被驱逐项记原始位置；read/grep/glob 重跑即恢复 |
| 4 有损摘要 | 摘要前先做全量存档，原文永不丢失 |

关键点：**恢复机制不是「尽力而为」，而是有校验的**。第 1 层的逆变换如果对不上会直接抛错，而不是静默返回错内容。

### 原则二：被取代引用记谱系，不静默删

任何内容被折叠/落盘/驱逐/摘要取代，都在谱系表登记三元组：

```
原位置  →  新位置  →  取代者
node#42 →  archive/xxx.txt  →  spill-to-disk
```

这让「这条信息去哪了」永远可回答。没有谱系表的压缩系统，一旦出问题只能靠猜。

### 原则三：压缩系统自身有熔断器与仲裁器

**压缩层不能成为新的故障源。** 所以：

- 单层连续失败达阈值 → 熔断该层，自动降级跳过并告警，主流程拿到原文继续
- 冷却期后放一次试探调用，成功即恢复
- 仲裁器决定内容归属哪层，避免多层重复处理

这条原则来自一个具体的教训：压缩是「为了帮忙」而存在的旁路，它挂掉绝不该拖垮主会话。

## 四、旁路管线：目标切换清理

除四层主管线外，还有一条**确定性旁路**（`goal-switch.js`），处理「任务切换时旧上下文怎么办」。

```
显式宣告新目标（结构化事件）
        │
        ▼
打包旧目标状态 → 结构化胶囊（todo / goal / plan）
        │
        ▼
过程性内容（大输出、中间产物）→ 归档到会话目录
        │
        ▼
零 LLM 调用
```

设计上刻意**只认显式信号**，不做语义自动识别。原因是自动判定「用户是不是换话题了」误判率太高，误清理的代价远大于收益。

## 五、与宿主的关系：服务位竞争

DSH 的 `compaction` 服务位是**单槽**——官方 basic、glm、kiro 等实现都往这一个位置挂。这是本插件必须处理的核心约束。

```
                    ctx.compaction（单槽）
                            │
              ┌─────────────┴─────────────┐
              │                           │
        enabled = false            enabled = true
              │                           │
              ▼                           ▼
    只注册只读自检服务           construction-catch 探测
    （tieredCompaction）                │
              │                  ┌──────┴──────┐
              │                  │             │
              │              槽位空闲      槽位被占
              │                  │             │
              │                  ▼             ▼
              │            接管服务位   降级「1-2 层旁路模式」
              │            （四层全跑）   （折叠+落盘照跑，
              │                            3-4 层挂起）
              ▼
        与 basic 完全并存
        行为零变化
```

### 为什么用 construction-catch 而不是 `ctx.get`

探测槽位占用有两条路，只有一条是安全的：

| 做法 | 结果 |
|---|---|
| `ctx.get('compaction')` | ❌ 会**强制实例化**懒声明的引擎，把槽占掉反噬自己 |
| 直接构造服务类，catch 注册冲突 | ✅ 冲突时抛错，catch 住后解析持有者再降级 |

这是 headless 环境实测踩出来的坑。`ctx.get` 看似是「查询」，实际是「创建」——用它探测等于自己把槽占了，然后判定「被占用」。

### 降级为什么是「1-2 层旁路」

第 1-2 层（折叠、落盘）与任何压缩形态都不冲突——它们只是把工具输出的体积压小，不碰会话结构。所以槽位被占时：

- 第 1-2 层**继续工作**（仍然省 token）
- 第 3-4 层**挂起**（这两层要改会话表面，与别的引擎会打架）

这是「不抢不炸」的实际含义。

## 六、接入宿主：观察者模式

宿主的工具结果以 `session/event` 流的形式产生。本插件通过观察者接入，而不是改造工具层。

```
宿主 append  tool/result 事件
        │
        ▼
 session/event 钩子（同步派发，不 await）
        │
        ▼
 ToolResultObserver.handleEvent
        │
        ├── 排除自身写回的替换事件（防递归）
        ├── 按会话隔离去重（防重复处理）
        ├── await 之前先占位（防并发竞态）
        │
        ▼
 第 1-2 层处理（折叠 → 落盘）
        │
        ├── 无收益 → 直接返回
        └── 有收益 → 写回会话表面
                        │
                        ▼
              ① append compaction/prune（影子定价）
              ② append tool/result + surfaceOp:replace（替换）
```

### 两个必须遵守的宿主约定

**1. 影子定价必须先于 replace，且中间不能插入别的事件**

宿主的 `token-meter` 会做严格校验：replace 事件的 range 必须与紧邻的影子定价 claim 完全一致，否则抛 `has no adjacent shadow price`。

由于 `session/event` 监听器是**同步派发、不 await 返回值**的，任何跨过 await 的间隙都可能被别的事件插入。所以「影子定价 + replace」两步必须紧贴在一起写。

**2. 只替换 tool/result，不动 assistant tool-call**

替换工具结果本身不会破坏 tool-pairing（call/result 配对）；但一旦替换到 assistant 消息，配对关系就可能断裂，导致宿主判定会话损坏。

## 七、关键设计取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| 摘要触发点 | 窗口 − 16k/5% 保护 − 20k 预留 | 预留必须显式扣减，否则摘要自己会撑爆窗口形成死循环 |
| 摘要输入 | 不先截断 | 先截断再摘要会丢掉长消息中部的事实，而那是信息密度最高的部分 |
| 落盘阈值 | UTF-8 字节数而非字符数 | 中文 1 字符 = 3 字节，按字符算会让 8,000 汉字（24 KB）漏落盘 |
| 预览长度 | 固定 5120 字符（头尾 4:1） | 对齐官方 pruner 口径，可预期；极端长文的信息损失由「全文在存档」兜底 |
| 去重集合 | 按会话隔离（WeakMap） | 进程级 Set 按 seq 记账会导致「第一个会话之后静默失效」 |
| 压力读数 | `request/context` 事件取窗口 | 真实 `TokenMeter` 没有 `contextWindow()` 方法，走错方法会让压力恒为 0 |
| 摘要调用 | `ctx.llm.stream()` | 真实 llm 服务没有 `summarize` 方法；且 stream 能复用服务端 prefix cache |
| 槽位探测 | construction-catch | `ctx.get` 会强制实例化、自占槽位 |

## 八、故障与降级设计

压缩是旁路，**任何情况下都不能拖垮主会话**。所有故障路径都收敛为「降级」而非「上抛」：

| 故障 | 处理 |
|---|---|
| 单层连续失败 | 熔断该层，主流程拿原文继续 |
| 观察者处理异常 | 记 warning，不加工，会话照常 |
| 槽位被占 | 降级 1-2 层旁路模式 |
| 摘要返回空 | 拒绝提交事务，补配对 `compaction/end` |
| 摘要比原文还大 | 拒绝提交（防止越压越大） |
| 压力读数不可得 | 退回保守路径，不强行触发 |

## 九、已知边界

- **宿主版本绑定**：契约层对齐 DSH 0.2.x 的 `CompactionEngine` 接口，宿主大版本升级需重新核对方法面。
- **只处理纯文本工具结果**：含图片/附件的富块一律跳过，避免破坏结构。
- **压力读数依赖 `request/context` 事件**：provider 不吐该事件时退回保守路径。
- **预览是固定预算**：超大输出的信息损失是设计上接受的代价——原文永远在存档里。

## 十、设计思想的两个来源

- **四层递进 + 保真三原则 + 目标切换旁路**：借鉴 `pi-maestro-flow` 的 compaction 模块思想（只搬思想，不搬代码——它深度绑定 Pi 的 API）。
- **工具结果替换的落地范式**：对齐 DSH 官方 `dsh-compaction-tool-result-pruner` 的两步写法（影子定价 → surfaceOp replace），保证与宿主投影、计量链兼容。
