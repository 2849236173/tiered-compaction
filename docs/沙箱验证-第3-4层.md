# D17 沙箱验证：第 3-4 层真实触发

**状态**：方案已实测确认可行（2026-10-27 09:30），尚未执行完整跑批。

## 为什么需要这个脚本

主环境验证不了第 3-4 层：桌面 profile 的模型窗口是 1,000,000 token，
当前会话压力约 3%。要触发 70% 提醒需要灌 70 万 token、80% 驱逐要 80 万、
第 4 层摘要阈值在 82%——成本和时长都不值当。

本脚本的做法：**在隔离 profile（m6h）里把窗口压小**，让少量 token 就能造出
真实压力。全程不碰主 desktop profile。

## 为什么不能用假 meter

D16 的三条实锤里有一条就是「测试桩伪造了宿主不存在的 API
（`meter.contextWindow()`）」，导致压力恒为 0、第 3 层永不触发。
本方案**用真实 host、真实 tokenMeter、真实事件流**，只把「模型窗口」
这一个业务参数调小。这是唯一允许改的东西。

## 实测确认的事实（2026-10-27 09:30 核实，非推测）

### ✅ 1. 窗口可以在哪改

**不能**改 `llm-pi-ai.providers.*.models[].contextWindow` —— m6h 的
`llm-pi-ai` 根本没有 config，模型窗口不在那里。而且实测发现：一旦在 patch 里
写 `providers`，**整个 providers 对象会被替换**（7 个 provider 只剩 1 个），
其他 provider 全丢，属于严重副作用。

**正确位置**：`llm-deepseek` 的 `defaultContextWindow`
（`dsh-llm-deepseek/lib/index.js:328`，默认值 `1e6`，即 100 万）。

实测覆盖写法（**已生效**，且无副作用——它是独立配置条目）：

```yaml
- id: llm-deepseek
  config:
    defaultContextWindow: 20000
```

> ⚠ 踩过的坑：本文件初版写成数组形式的 `providers: [{...}]`，与实际
> 结构（对象，provider id 作键）不符。**patch 写法必须以 `--dump-config`
> 实际合成为准**，不能凭猜。

### ✅ 2. CLI 不要用环境变量

`$env:DSH_PROFILE` **无效**——设了它之后 `dsh --dump-config` 读的仍是
desktop 的 patch（会看到 desktop 专属条目和报错）。正确用法是命令行参数：

```powershell
dsh --profile m6h --dump-config
dsh --profile m6h --dump-config --patch <覆盖文件>
```

### ✅ 3. m6h 具备造压所需的一切

| 需要的东西 | m6h 状态 |
|---|---|
| `agent-loop`（驱动 `agent/pre-step` 钩子） | ✅ 在 |
| `credentials`（读 API key） | ✅ `disabled: false` |
| `tiered-compaction` | ✅ `enabled: true`，`archiveDir` 已配 |
| 默认模型 | `deepseek-flash`（走 `llm-deepseek`） |

### ⚠ 4. 一个未确认的前提

`defaultContextWindow: 20000` 只改「宿主认为的窗口大小」，实际模型仍有 100 万
真实容量。这意味着**不会真的撞窗**，压力是我们「让它以为」的。
对验证第 3-4 层的触发逻辑而言这足够了（我们验的就是触发判定），
但**不能**据此声称「验证了真实溢出恢复」。

## 执行步骤

### 第 1 步：写覆盖文件

```powershell
$patch = "$env:TEMP\m6h-smallwindow.yml"
@'
- id: llm-deepseek
  config:
    defaultContextWindow: 20000
- id: tiered-compaction
  config:
    enabled: true
    archiveDir: C:\Users\asus\.dsh\tiered-archive-sandbox
'@ | Set-Content $patch -Encoding utf8

# 必须核对合成结果，不能假定生效
dsh --profile m6h --dump-config --patch $patch |
  Select-String -Pattern 'defaultContextWindow|tiered-compaction' -Context 0,3
```

### 第 2 步：跑一段会持续消耗上下文的任务

headless 模式一次一任务，任务本身要能撑到足够 token：

```powershell
dsh --profile m6h --patch $patch "读遍当前目录下所有 .js 文件，逐个输出完整内容并统计行数，最后给汇总表"
```

要靠任务自然累积到 1.4 万 token 以上。小窗口下这很快（约 30~40 个文件）。

### 第 3 步：读结果

**日志判据**（`%APPDATA%\DSH Desktop\logs\host\dsh-<日期>.log`）：

| 层 | 搜这段文本 |
|---|---|
| 第 3 层提醒 | `（70%），建议收束当前任务` |
| 第 3 层驱逐 | `（80%），已广播易失内容驱逐事件` |
| 第 4 层摘要 | `有损摘要完成（budget=` |
| 护栏生效 | `compaction already in progress`（正常流程不该出现） |

**独立证据**（不依赖日志文本，更硬）：

- 第 4 层：会话事件流里必须有配对的 `compaction/start` … `compaction/end`，
  中间有 `compaction/summary`；表面上原区间被替换成 checkpoint 消息
- 摘要前必须有全量存档落盘（`lossy-summarize` 的 archivePath）
- 第 3 层驱逐：广播事件 `tiered-compaction/evict` 有监听者才算真落地

### 第 4 步：清理

```powershell
Remove-Item "$env:TEMP\m6h-smallwindow.yml"
Remove-Item 'C:\Users\asus\.dsh\tiered-archive-sandbox' -Recurse -Force -ErrorAction SilentlyContinue
```

（m6h 的 patch 未改，无需回滚。）

## 窗口 20000 时的理论触发点

由 `src/lossy-summarize.js` 实算：

| 累计 token | 占比 | 应触发 |
|---|---|---|
| < 14,000 | < 70% | 无动作 |
| ≥ 14,000 | ≥ 70% | 第 3 层提醒 |
| ≥ 16,000 | ≥ 80% | 第 3 层驱逐 |
| ≥ 16,400 | ≥ 82% | 第 4 层摘要（82% 是下限，见阈值公式说明） |

## 红线

1. **不得修改主 desktop profile** 的任何文件
2. **不得伪造 tokenMeter**（D16 教训：桩失真会让整层静默失效）
3. 只允许改「窗口大小」这一个业务参数
4. 失败就如实记录「未触发 + 原因」，**不要为了让验证通过而降低判据**
5. 验证完清理沙箱产物

## 如果第 3-4 层仍不触发，优先怀疑什么

按今晚踩过的坑排序：

1. **观察者/钩子没接上** → 查日志有无「观察者已注册」，以及 `session/event` 是否被真实派发
2. **窗口读数没生效** → 查 `contextWindowOf` 是不是读到了 `request/context` 事件里的 `data.contextWindow`；若 dump 有 `defaultContextWindow` 但会话事件流里没有 `request/context`，压力仍会是 0
3. **阈值算错** → 直接调 `lossyThreshold(20000)` 核对应为 16400
4. **pre-step 没被驱动** → 查 headless 的 agent-loop 是否真的逐步执行
